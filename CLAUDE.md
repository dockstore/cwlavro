# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CWL Avro (`io.cwl:cwlavro`) demonstrates auto-generating Java classes from the Common Workflow
Language (CWL) specification via Avro, then using them to parse real CWL documents (which are not
plain JSON/Avro) into typed Java objects. It's a 2-module Maven reactor build, now in maintenance
mode for Dockstore support — new users are pointed to
[cwljava](https://github.com/common-workflow-lab/cwljava) for CWL v1.2 support instead.

## Dependency conventions

Prefer, in order: (1) built-in Java 17 features, (2) a third-party library already pulled in via
Maven elsewhere in the project, (3) a new third-party dependency — only reach for a new one when
neither of the above covers the need.

## Branching

The repo follows Hubflow (gitflow) conventions: `develop` is the main integration branch (this
repo's default branch for PRs), with work done on `feature/*` branches branched from and merged
back into `develop`, `hotfix/*` branches for urgent fixes, and `release/*` branches cut for
releases.

## Pull requests

When creating a PR, always create it in draft mode. A human developer must be the one to mark it
ready for review/move it out of draft state — Claude Code should not do this itself.

Keep the freeform "Description" and "Review Instructions" sections brief — one paragraph each, or
two for a genuinely complicated fix, not multi-paragraph writeups.

## Build / test commands

Requires Maven 3.1+ and Java 17. Building/testing also requires `cwltool` on the `PATH`, since
tests shell out to it to parse CWL documents (see Architecture below):

```
pip install --user setuptools==28.8.0
pip install --user cwl-runner cwltool==1.0.20170217172322 schema-salad==2.2.20170222151604 avro==1.8.1
```
(CI installs newer pinned versions instead — see `.github/workflows/build.yaml`.)

- Full build + test: `mvn clean install`
- Build without tests: `mvn clean install -DskipTests`
- Run all tests in a module: `mvn -pl cwlavro-tools test`
- Run a single test class: `mvn -pl cwlavro-tools test -Dtest=CWLToolTest`
- Run a single test method: `mvn -pl cwlavro-tools test -Dtest=CWLToolTest#stubArrayWithId`
- Generate Javadoc: `mvn javadoc:javadoc`

There is only one concrete test class, `cwlavro-tools/src/test/java/CWLToolTest.java`; it and the
shared test logic in `AbstractClientTest` both live directly under `src/test/java` with **no
package declaration** — keep new tests there consistent with that.

## Architecture

Two Maven modules, `cwlavro-generated` depended on by `cwlavro-tools`:

- **`cwlavro-generated`** — Avro-generated Java model classes for every CWL schema type
  (`CommandLineTool`, `Workflow`, `CommandInputParameter`, `File`, `Directory`, etc.), all in
  package `io.cwl.avro`. These files carry `Autogenerated by Avro / DO NOT EDIT DIRECTLY` headers
  and are checked in rather than generated at build time — the regeneration procedure itself is
  documented as a series of manual/CI steps (see "Regenerating the schema" below and
  `.github/workflows/build.yaml`), not something invoked from the Maven build.
  - A handful of classes collide in name with a Java package the schema generator also produces
    (`ArraySchema`, `Directory`, `EnumSchema`, `File`, `RecordSchema`). The fix used throughout the
    codebase is to rename the conflicting subpackage to `...Package` (e.g. `Directory` the class
    vs. `DirectoryPackage.class$.Directory_class` for the nested type) — this is done by the CI
    regeneration script, not by hand.
  - The CWL `Any` type is special-cased: it's generated as an enum by avro-tools, which breaks
    instantiation, so it's deleted and all references are rewritten to plain `Object`.

- **`cwlavro-tools`** (`io.cwl.avro` package under `src/main/java`) — runtime helpers that bridge
  real-world CWL documents to the generated model classes:
  - `CWL.java` — the main entry point. `parseCWL()` shells out to `cwltool --non-strict --print-pre`
    (via `Utilities.executeCommand`) to normalize a `.cwl` file into JSON, since CWL documents
    aren't directly JSON/Avro-compatible. `getTypeSafeCWLToolDocument()` builds a custom `Gson`
    with hand-registered `TypeAdapter`s for every collection-typed CWL field (inputs, outputs,
    hints, step inputs, etc.), because CWL's JSON-LD-ish encoding (fields that are sometimes an
    array, sometimes an id-keyed map) doesn't map onto plain Gson reflection —
    `gsonBuilderHelper()` is the shared logic for both cases. `extractRunJson()` /
    `extractCWLTypes()` turn a parsed `CommandLineTool` into a stub input/output JSON (a "fill me
    in" parameters template) and a type map, respectively; `getStub()` is the recursive CWL-type →
    default-value mapper used to build those stubs (handles both cwltool's `{type=array,
    items=File}` map-ish rendering and bunny's `File[]` string rendering of array types).
  - `Utilities.executeCommand()` — thin wrapper around Commons Exec for running external processes
    and capturing stdout/stderr as an `ImmutablePair`.
  - `CompressionUtilities.java` — archive extraction helpers.
  - Tests (`AbstractClientTest` + `CWLToolTest`) exercise `CWL` end-to-end against real `.cwl`
    files in `src/test/resources` (`valid.cwl`, `invalid.cwl`, `arrays.cwl`, `nullDefault.cwl`,
    etc.), i.e. they require a working `cwltool` install to pass.

### Regenerating the schema

The generated sources in `cwlavro-generated` are produced from the upstream CWL spec via
schema-salad → Avro schema → `avro-tools` codegen, with several manual/scripted fixups (deleting
draft-version enum symbols, the `Any`-type and package-collision fixes described above). The exact,
current sequence of steps lives in `.github/workflows/build.yaml` (job `Build`) — treat that
workflow file as the source of truth over the older narrative version in `README.md`, since the
tool versions there have drifted (e.g. `cwltool`/`schema-salad` versions differ between the two).
